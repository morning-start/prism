## 0. 项目章程（G0 产物，2026-10-25 规范化时定稿）

### 0.1 目标表述

**Prism 是一个中立 LLM 协议转换引擎（MoonBit 实现）**：任意厂商的 JSON/SSE 请求与响应
先 decode 进中立中间表示 **Lucent IR**，再 encode 到目标协议；永不编写两两转换器。

- 一句话电梯稿：*把"每对协议写一个转换器"的 N×N 问题，变成 N 个 decode + N 个 encode
  的 2N 问题，并且每一次信息损失都是显式诊断，绝不静默丢弃。*
- 差异化主张（三 pillars）：
  1. **中立 IR** —— `src/lux` 与任何厂商零耦合，中间层可编程（审计/改写/路由/过滤）。
  2. **显式保真度** —— 每个字段/事件都有 `Exact / Degraded / Unsupported / Invalid`
     边界（`docs/fidelity-matrix.md`），配套诊断与策略熔断。
  3. **可证伪的正确性** —— 官方 SDK schema 作裁判的 Node oracle
     （`tools/conformance/`），"与官方协议一致"可被机器验证。

### 0.2 目标用户与核心场景

| 用户 | Providers 用量 | 核心场景 | 痛点（现有替代方案的问题） |
|------|---------------|----------|---------------------------|
| Agent 框架开发者（SDK 型） | 1 个 | `IR → ProviderA` 发出、`ProviderA → IR` 接收 | 换模型/协议要改代码；官方 SDK 互相不兼容（替代：官方 SDK 直连单协议） |
| 中转/网关开发者（middleware 型） | 2+ 个 | `PA → IR → PB`，或 `PA → IR → PA` 做审计/改写/限流 | Python 网关（LiteLLM 等）不可嵌入、静默降级难审计（替代：自研胶水代码） |
| WASM 宿主（插件/浏览器/边缘） | 1+ 个 | 字符串 ABI 进出，零编组转换 | 无编译型、可嵌入沙箱的协议转换器（替代：JS 层手写适配） |

### 0.3 成功指标（业务验收依据）

| 指标 | 当前基线（2026-10-24） | M1 目标 | 度量方式 |
|------|----------------------|---------|----------|

## 2. 需求条目

### REQ-001 wrappers 接入（M1 主线）

- **目标用户**：TS / Go 侧消费者；CI 维护者
- **核心场景**：Node/浏览器通过 TS wrapper 消费 wasm 产物完成协议转换；未来 Go 宿主
  走字符串 ABI
- **痛点与现有替代方案**：目前外部使用者只能自己拿 wasm 导出手写胶水；历史记录曾声称
  wrappers Complete 但仓库快照无此目录，信息不可信
- **用户澄清（2026-10-25）**：**还没做好，是问题很大的部分，后面再做** → 排 M1 后段，
  POC 先行，不承诺工期；对外发布承诺继续冻结直至 1.3 完成
- **MVP 范围**：单语言（TS 优先）端到端链路：wasm 构建产物 → wrapper 包编译 → 最小
  集成测试（至少覆盖 1 次请求转换 + 1 次流式转换）→ CI 接入
- **非目标**：MVP 不做双语言全覆盖、不做 npm 发布流程、不做 API 稳定性承诺
- **假设（待验证）**：~~TS wrapper 直接 import wasm-gc 产物即可，无需 wasm-pack 中间层~~
  **已验证（POC-1，2026-10-25）**：裸 import 可行，Node ≥ 22
- **进展（2026-10-25 晚 PM 更新）**：主链路已通 —— POC → 2b 修复 → 2c CI 冒烟 →
  wrapper 落库全部 QA 验收通过；剩余 TASK-4b（decode 形状守卫，**阻塞发布**，排期第 1
  位）、TASK-5（CI 集成，第 2 位）、TASK-6（发布解冻评审）。收尾排期见 05-任务板
  「排期总览」
- **状态**：开发中（M1 收尾段）；4b+5+6 完成 → 待验收
- **业务验收标准**：见 `07-验收标准与用例.md` ACC-001
- **成功指标**：CI 全绿且含 wrapper 集成测试 job；USAGE.md 中 wrapper 示例可复现
- **风险与依赖**：RISK-001（POC 后实质缓解，待 1.5 评审关闭）；RISK-004 已关闭（POC
  结论替代）；衍生 TD-004/005/006 见 06

### REQ-002 IR Evolution Backlog 治理（M2）

来自 2026-09 跨协议审计（`docs/status.md` §IR Evolution Backlog）。四项 adapter 级
缓解已就位，IR 级载体待治理：

| # | 项 | 现状 | 优先级建议 |
|---|---|---|---|
| 1 | ToolResult name carrier（`LucentToolResult` 仅 `tool_use_id`，gemini 需预扫描重建 id→name map） | 已缓解 | 中 |
| 2 | Reasoning continuation credential side-channel（responses `reasoning.encrypted_content` 无 IR 载体，decode 打 Degraded 诊断） | 已缓解 | 中 |
| 3 | ReasoningEffort `Minimal` tier（openai `minimal`→Low；anthropic `max`→XHigh） | 已缓解 | 低 |
| 4 | `parallel_tool_calls` 标准字段提升（现经 extras 语义反传，SDK 侧已有 `with_parallel_tool_calls`） | 已缓解 | 中 |

- **目标用户**：Prism 自身可维护性；跨端保真度
- **痛点**：预扫描与 extras 反传是隐性契约，新 adapter 容易漏
- **MVP 范围**：每项独立出治理提案（影响面声明 + Exact/Degraded 边界 + 跨端回归测试），
  按 `docs/rules/lucent-ir-evolution.md` 流程裁决；单提案可独立交付
- **非目标**：不捆绑打包四项一起上；不因 SDK 人体工学推翻保真度硬门禁
- **业务验收标准**：见 `07-验收标准与用例.md` ACC-002
- **状态**：待澄清（M2 触发后再逐项推进）
