## POC 记录

```
### POC-1 wrapper 技术选型（已执行 2026-10-25，TL；脚本 .agent-team/poc/task2-node-load.mjs）
- 假设：TS 直接 import MoonBit 编译的 wasm-gc 产物即可完成字符串 ABI 调用，
  无需 wasm-pack 中间层
- 验证方式：Node v24.21.0 原生 WebAssembly.compile 加载 `moon build
  --target wasm-gc` 产物（debug 651KB / release 302KB），检查导出表并
  尝试调用 wasm_abi_version / wasm_convert_req（openai→messages）
- 结果：**假设被部分推翻**。wasm-pack 不是问题（Node 24 原生支持 wasm-gc，
  import 机制本身通畅），但产物当前**无法通过 V8 校验**，两个独立缺陷：
  1) src/cmd/main/moon.pkg 的 link.exports 只声明了 "wasm" 后端，
     没有 "wasm-gc" 块 → wasm-gc 产物从未含 28 项 ABI 导出（仅 _start）。
     【TL 已补 wasm-gc exports 块，随 POC 提交】
  2) 阻塞级：src/wasm/memory.mbt 的 scratch/log ABI 用 `= "%identity"`
     把 Int32 强转为 Bytes / FixedArray[Byte] 引用（线性内存指针技巧，
     仅纯 wasm 后端成立）。wasm-gc 下这些是 GC 托管 (ref n) 类型，
     V8 校验拒绝整个模块：
       debug:   #92 "_M0FP…log__write" failed: local.set[0] expected
                type (ref 2), found local.get of type i32
       release: #44 failed: type error in fallthru[0] (expected i32,
                got (ref 2))
     受影响导出：wasm_init_scratch / wasm_read_scratch_arg /
     wasm_log_init / wasm_log_pos / wasm_convert_*_trace 共 6 个；
     其余 22 项导出逻辑不被该缺陷污染（测试套件未覆盖 memory.mbt，
     故 1442 tests 全绿仍通过——moon test 的 wasm-gc runner 不校验
     主模块导出段）。
- 结论：REQ-001 MVP 链路**可行**（直接 import，无需 wasm-pack），但
  前置一个 wasm-gc 后端修复任务：memory.mbt 的 6 个 scratch/log 导出
  需重写为 wasm-gc 合法形态。两个候选方案（见 05-任务板 TASK-2b）：
  A. 按后端条件编译：wasm-gc 下 scratch/log 返回错误信封
     {"error":"unsupported on wasm-gc"} 或降级为纯 MoonBit 堆实现，
     保住 22 项转换导出先通链路；
  B. 完整修复：用 wasm-gc 合法方式重建大字符串/日志通道
     （例如经 String 编码协议而非线性内存指针），工期更大。
  建议：先 A 后 B（A 是 MVP 阻塞清障，B 列技术债）。
- 环境备注：Node ≥ 22 即可（wasm-gc 无需 flag）；本机 mise shim 在
  bash 下偶发 rust 安装报错不影响 node/moon 本体。
```
