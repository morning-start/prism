## 验收标准

### ACC-001 —— REQ-001 wrappers 接入（M1 主线）

**业务验收（PM 主导）**
- [ ] Node 环境通过 TS wrapper 完成 ≥1 次**请求**跨协议转换（如 openai→messages），
      输出与 `src/sdk` 直连结果一致
- [ ] 完成 ≥1 次**流式**转换：逐 chunk feed 产出逐帧事件，`finish()` 后尾部帧完整
      （CR-002 终止符契约在 wrapper 层可见、可调）
- [ ] 诊断可透出：人为构造触发 Degraded 的输入，wrapper 调用方能拿到诊断对象
- [ ] wrapper 有最小 README：安装/初始化/1 个请求示例/1 个流式示例/错误处理示例
- [ ] USAGE.md 的 wrapper 章节与实际行为可复现

**非功能验收（TL 参与）**
- 构建：`moon build wasm` 产物版本固定，wrapper 锁定对应 `wasm_abi_version`
- CI：新增 job = wasm 构建 → wrapper 编译 → 集成测试，与主测试并行可跑
- 兼容性：POC 确定的最低 Node 版本写入 package.json engines
- 回滚：wrapper 目录独立成包，回滚不影响 core 测试

### ACC-002 —— REQ-002 IR 载体治理（M2，逐项独立验收）

**业务验收（PM 主导，单提案通用）**
- [ ] 治理提案含：影响面声明、Exact/Degraded/Unsupported 边界、是否破坏性变更判定
- [ ] 提案实施后 fidelity-matrix 相应格升级且矩阵文档同步
- [ ] 跨端回归测试：涉及的两端（或四端）逐格断言，含反向验证（回退即红）

**非功能验收（TL 参与）**
- 破坏性提案按 CR-006 先例走版本号（0.x → 0.(x+1).0）
- 覆盖率余量不被吃穿（阈值 204 行，见 RISK-003）

### ACC-003 —— REQ-003 capability 声明修正（M1 热身）

**业务验收（PM 主导）**
- [ ] openai-chat / responses / messages 三处 capability 声明与协议真实能力一致
- [ ] `docs/fidelity-matrix.md` §1 同步更新
- [ ] 现有 extras 反传测试全绿，无行为变化（纯声明修正）

## 缺陷分级与关闭标准

- **P0**：转换结果语义错误 / 数据静默丢失 / 流挂起或崩溃 —— 阻塞发布，清零后才能发布
- **P1**：保真度降级未给诊断（违反「绝不静默丢弃」）/ wrapper 诊断不可达 —— 清零后才能发布
- **P2**：文档漂移、诊断文案、兼容性边角 —— 有规避方案即可发布，登记回归清单

## DoR（可开发条件）

- 需求有目标、场景、优先级、MVP 边界（00-需求池条目齐备）
- 有业务验收标准（本文件 ACC 编号）和非功能要求
- 有技术方案、接口/数据契约（04）、估算（TL 回填 05-任务板）
- 风险与依赖已登记（06）
- QA 验收用例草案已就绪（本文件 TC 编号）

## DoD（可发布条件）

- 功能验收通过（ACC 逐条勾选）
- 非功能项达标或有明确豁免
- P0/P1 清零，P2 有规避方案
- 文档更新（status.md / fidelity-matrix / 05-任务板 / 08-验收报告）
- 回滚方案已验证（wrappers 独立成包）
- QA 验收报告签字，PM 业务确认，TL 技术确认
