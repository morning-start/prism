## 1. 方法论

### 1.1 调研范围

本报告覆盖 **跨语言/跨进程服务调用** 的全部可行方法，按通信层次分类。不限定于特定操作系统或编程语言。

### 1.2 评估维度

每个方法从以下维度评估在 Prism 中的适用性：

| 维度 | 含义 |
|------|------|
| **Prism 适配度** | Prism 是纯函数转换引擎，该方法能否自然匹配 |
| **流式支持** | 能否传递 SSE Token 流 |
| **跨语言广度** | 支持多少种语言 |
| **部署开销** | 额外依赖、进程、配置 |
| **性能** | 端到端延迟、吞吐 |

## 3. 完整方法清单

### 3.1 进程内嵌入

共用同一进程地址空间，调用方与 Prism 之间无进程边界，延迟最低。

| # | 方法 | 原理 | 延迟 | 跨语言 | 流式 | 备注 |
|---|------|------|:----:|:------:|:----:|------|
| 1 | **WASM 模块** | 编译到 .wasm，各语言 WASM Runtime 加载 | μs | **大部分** | 中等 | ✅ **Prism 已实现** |
| 2 | **WASM Component Model** | WIT 接口描述，各语言自动绑定 | μs | 少（生态早期） | 好 | 未来标准 |
| 3 | **C ABI 动态库 (.so/.dll/.dylib)** | 导出 C 函数，各语言 FFI 调用 | ns | **全部** | 中等 | 性能天花板 |
| 4 | **dlopen/LoadLibrary 插件** | 运行时动态加载，符号查找 | ns | C/C++ 为主 | 中等 | |
| 5 | **JNI** | Java 调用 native C | ns~μs | Java↔Native | 中等 | Java 专属 |
| 6 | **JNA** | Java 调用 native（纯 Java 实现） | μs | Java↔Native | 中等 | 比 JNI 慢但无 C 代码 |
| 7 | **P/Invoke** | .NET 调用 native | ns | C#↔Native | 中等 | .NET 专属 |
| 8 | **CGo** | Go 调用 C | 50ns | Go↔C | 中等 | Go 专属，有调度开销 |
| 9 | **N-API (Node.js Native Addon)** | Node 调用 native | ns | Node↔C | 中等 | Node 专属 |
| 10 | **Python C Extension** | Python 调用 C | ns | Python↔C | 中等 | CPython 专属 |
| 11 | **libffi / ctypes** | 调用任意 C ABI 函数 | μs | 大部分（动态） | 中等 | |
| 12 | **SWIG 代码生成** | 接口定义 → 自动生成胶水代码 | ns | 大部分 | 中等 | 自动化绑定生成 |
| 13 | **IDL 代码生成 (Protobuf/Thrift)** | IDL → 桩代码 | ns | 大部分 | 好 | 通常用于 RPC |
| 14 | **多语言交叉编译** | 同一源码→多目标语言 | ns | 取决于编译器 | - | 罕见 |

> **关键对比：WASM vs C ABI**
> - WASM：沙箱安全、单二进制分发、无平台依赖、但 WASM-GC 生态受限
> - C ABI：性能最高、所有语言都支持、但需为每个平台单独编译、AOT 加载

## 4. Prism 适配分析

### 4.1 Prism 的核心约束

在选择对外服务方法前，先明确 Prism 这个项目的 **固有特征**：

```
┌─────────────────────────────────────────────────────────────┐
│                  Prism 项目的固有约束                          │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  🔹 纯函数引擎                                                │
│     └─ 无状态、无 IO、无副作用                                  │
│     └─ 唯一的 IO 是 WASM 导出函数调用                           │
│                                                              │
│  🔹 数据接口已固定                                             │
│     └─ 输入：String JSON                                      │
│     └─ 输出：String JSON                                      │
│     └─ 11 个通用函数签名已定型                                  │
│                                                              │
│  🔹 需要流式支持                                              │
│     └─ SSE 事件解码/编码核心能力                                │
│     └─ 调用方需要逐 token 消费流                                │
│                                                              │
│  🔹 调用频次                                                  │
│     └─ 每次 LLM 调用都要经过 Prism                              │
│     └─ 可能在热路径上（每次 API 请求）                           │
│                                                              │
│  🔹 部署形态                                                   │
│     └─ 目标用户：AI 应用开发者                                  │
│     └─ 需要：极简集成、零运维                                   │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 分层评估

将全部 92 种方法按三个粒度评估：

#### 第一层：即时淘汰 ❌

这些方法与 Prism 特征明显冲突：

| 方法 | 淘汰原因 |
|------|---------|
| COM/DCOM (#26) | Windows 锁定，跨平台项目 |
| CORBA (#27) | 遗留企业中间件，过于重量级 |
| Android Binder (#28) | Android 专用 |
| Mach Ports (#29) | macOS 专用 |
| SOAP/XML-RPC (#43, #44) | 遗留协议，重量级，XML 与 JSON 不匹配 |
| Java RMI (#48) | 仅 Java |
| .NET Remoting/WCF (#49) | 仅 .NET |
| Dubbo (#47) | Java 生态为主 |
| tRPC (#50) | TypeScript 仅 |
| 硬件级方法 (#87-#92) | Prism 纯函数引擎不需要硬件直通 |
| Multi-VM (#77-#80) | Prism 自己就是独立编译单元，不需要共享运行时 |
| Cloud Native (#81-#86) | 基础设施层，Prism 运行在这些之上，而非取代 |
| Signal/eventfd/signalfd/filelock (#30-#33) | 数据量太小，不适合传递 JSON |
| System V IPC (#19, #22) | 遗留，功能被 POSIX 替代 |

#### 第二层：可以考虑，但优先级低 ⏳

| 方法 | 为什么可考虑 | 为什么优先级低 |
|------|------------|--------------|
| D-Bus (#25) | Linux 桌面通用 IPC | 非桌面项目，多平台受限 |
| CORBA 变体 | 部分企业仍有 | 生态消亡中 |
| Thrift/Avro (#41, #42) | IDL 代码生成强类型 | 需要维护 IDL 定义，Prism 已用 JSON |

### 5.2 为什么 WASM 是核心答案

Prism 选择了 MoonBit，而 MoonBit 的首选目标就是 WASM-GC。这个技术栈选择天然决定了 WASM 是**最优**而非"之一"的方案：

| 对比项 | WASM 嵌入 | IPC daemon | 网络 RPC |
|--------|-----------|------------|---------|
| 是否需要额外进程 | ❌ | ✅ Daemon | ✅ Daemon |
| 部署方式 | 单文件 `.wasm` | 二进制 + systemd | 二进制 + systemd + 端口 |
| 故障模式 | 无（同进程） | Daemon 挂了全不能跑 | Daemon 挂了全不能跑 |
| 版本管理 | 用户代码一起管理 | 单独管理 | 单独管理 |
| 延迟 | ~μs（函数调用） | ~10μs（IPC 序列化） | ~ms（网络） |
| 安全面 | 无网络端口 | 需管理 socket 权限 | 需网络鉴权 |

> **WASM 嵌入不只是"一种可行方案"，它是 Prism 这个项目架构的最优解。** 其他所有方案（Daemon、IPC、RPC 等）都引入了不必要的进程边界和运维复杂度，只应在 WASM 嵌入无法满足需求（如浏览器前端、跨语言进程共享、企业级集中管控）时才考虑作为补充。
