## 变更 1：`LucentFinishReason` 编码值对齐 schema（P0-3）

- **问题**：`LucentFinishReason::to_string` 输出 `"malformed_function_call"`，
  而 `schemas/lux-ir-v1.json` 的枚举法定值是 `"malformed_tool_call"`。
  按 schema 实现的第三方对端会拒绝本实现输出的响应文档；对端按 schema
  发出的 `"malformed_tool_call"` 读进后再编码出去仍变成非法值 —
  跨实现往返断裂。内部测试无法暴露（`from_string` 曾同时兼容两种拼写）。
- **变更**：
  - `src/lux/helpers.mbt`：`to_string` 输出 `"malformed_tool_call"`；
    `from_string` 保留 `"malformed_function_call"` / `"MALFORMED_FUNCTION_CALL"`
    的兼容读取（本仓库曾按此值输出，旧文档/存量对端可能仍在用）。
  - 回归：`src/lux/lux_wbtest.mbt` 锁定新输出值 + 新旧拼写均入栈。
- **迁移**：无需迁移——旧拼写仍可读入；输出侧只是修正为 schema 法定值。
- **风险**：存量下游若按旧值做字符串匹配会失配（但那是实现漂移导致的
  既存错误行为，修正后与 schema 一致）。

## 变更 2：`LucentMediaSource` schema 漂移修复（P0-2）

- **问题**：`schemas/lux-ir-v1.json` 把 `LucentMediaSource` 定义为字符串
  const 枚举（`"inline"|"url"|"file_uri"`），而 `LucentMediaSource::Inline`
  携带 base64 数据载荷——字符串 enum 无处安放数据，schema 本身不完整。
  实现自 `to_json`/`from_json` 起即为 `{"type":...,"data":...}` 对象形状，
  按 schema 发字符串的对端（`"source":"url"`）会被实现 `Err` 拒绝，
  整个多模态块反序列化失败。drift 检查器长期 skip 该类型掩盖漂移
  （`check_schema_drift.ps1` skip 列表）。
- **决策**：schema 对齐实现（对象形状是正确的——它表达了 `Inline` 的数据；
  字符串形状从未被实现支持过，不存在"用户"）。`data` 对所有三种 source
  均为必填（载荷本体）。
- **变更**：
  - `schemas/lux-ir-v1.json`：`LucentMediaSource` 改为对象数组 oneOf
    （`{type: inline|url|file_uri, data: string}`，均必填），
    description 记录漂移史。
  - `src/lux/deserialize_primitives.mbt`：`data` 缺失从默认 `""` 改为
    `Err`（"缺失"与"空数据"不再混为一谈，schema 亦必填）。
  - `scripts/check_schema_drift.ps1`：从 skip 列表移除 `LucentMediaSource`，
    该类型的漂移此后纳入检查。
  - 回归：`from_json_error_test.mbt` 锁定 data 缺失 Err + 对象形状
    round-trip。
- **迁移**：旧字符串形状无数据可用，无法也不需兼容（实现从未产生过它）。
- **验证**：`moon test` 全量 1216/1216；drift 检查器 report/strict 双 PASS。

## 不做的事（明确决策）

- 不新增字符串形状的兼容读取分支：它无法表达 `Inline` 数据，纯噪音。
- 不改 MoonBit 侧类型（`LucentMediaSource` 三变体 + `String` 载荷不变），
  公开 API 无破坏。
