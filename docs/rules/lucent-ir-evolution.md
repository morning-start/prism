# Lucent IR 演进与字段归类规则

本文规定 Prism Agent 在评估新 Provider 字段、内容类型、工具类型、流事件和传输能力时，如何决定其归属。

`docs/lux-ir-design.md` 是当前 Lucent IR 形式规范；本文是该规范的**演进治理规则**。二者冲突时，不得自行修改实现：先依据本文形成明确决策，再同步更新形式规范、实现和测试。

## 1. 目标与边界

Prism 不是所有 Provider 字段的并集，也不是最低公分母。Lucent IR 是一个面向消费方的、稳定的 LLM 对话与生成语义模型。

Agent 必须从 SDK 消费者的稳定义务反推 IR，而不是从单一 Provider 的 JSON 形状反推 IR。

各层职责如下：

1. **语义内核（Semantic Kernel）**：对话项、内容块、工具交互、结束原因、错误和流式生命周期。
2. **可移植控制（Portable Controls）**：跨 Provider 具有稳定等价语义的生成、推理和结构化输出控制。
3. **类型化孵化区（Typed Incubation）**：重要但语义尚未稳定、暂不适合冻结进核心的概念。
4. **Provider 扩展（Provider Extensions）**：Provider 专属请求参数和响应附载。
5. **传输层（Transport）**：HTTP、SSE、后台任务、轮询、超时、重试和连接生命周期。

## 2. 不可破坏的不变量

所有 IR 和适配器变更必须维护以下不变量：

1. **不静默丢失**：未知但可观察的语义节点必须进入有序的 `Native`/孵化表示，或返回明确错误；不得用空字符串、空数组、`None` 或忽略分支伪装成功。
2. **顺序保持**：会话项、内容块和流事件的相对顺序不得因适配而改变。
3. **身份保持**：工具调用、工具结果及其他关联事件的 ID 关系不得丢失或错误合成。
4. **行为等价**：在目标 Provider 支持的范围内，`Provider -> Lucent -> Provider` 必须保持可观察行为等价；不要求字节级 JSON 相等。
5. **已有语义稳定**：已发布变体和字段的含义不得在同一 schema major version 中改变。
6. **显式降级**：目标 Provider 无法表达某项语义时，适配器必须按规范报错、保留为扩展或执行已记录的有损降级；不得自行猜测。
7. **层次隔离**：网络调用生命周期不得进入对话语义；Provider 私有拼写不得泄漏进通用核心。

## 3. 五道判定门

不能只问“这个字段是否改变对话形状”。Agent 必须依次完成以下五项判断。

### 3.1 消费者义务

问题：正确的 UI、SDK、Agent loop、工具调度器、日志或安全组件是否必须理解它并采取不同动作？

- 是：它可能属于标准语义。
- 否：继续判断；它通常属于控制参数、附加数据或传输层。

“需要不同 `match` 分支”是强证据，但不是唯一证据。计费、安全、续接和无损转发也属于可观察义务。

### 3.2 无损与续接

问题：删除它以后，是否仍能正确理解、执行、续接并反向转换这次交互？

- 不能：至少必须进入类型化结构、`Native` 或扩展区。
- 能：可以留在 Provider 附载，或不进入 IR；但必须证明不会影响行为。

### 3.3 Provider 独立性

问题：不提 Provider 名称，能否用一句稳定的话定义它？

- 能：具备标准化候选资格。
- 不能：保留在命名空间化的 Provider 扩展中。

例如，“模型请求调用一个外部函数”具有 Provider 独立语义；“把某 Provider 的 `include` 原样发送”没有。

### 3.4 不变量与映射

问题：能否写出稳定的不变量，并为至少两个协议或一个协议的双向路径定义清晰映射？

- 能：可继续考虑标准化。
- 不能：概念尚未成熟，进入类型化孵化区或扩展区。

### 3.5 成熟度与兼容成本

问题：现有证据是否足以把该概念冻结进公共 API？

评估：

- 是否有真实请求、响应或 SSE fixture；
- 是否覆盖至少两个独立 Provider，或它本身是消费者不可回避的新语义；
- 是否有构造、序列化、反序列化、双向适配和流式映射方案；
- 是否知道目标 Provider 不支持时如何降级；
- 是否值得承担新增字段或枚举变体的兼容成本。

证据不足时，不得为了“以后可能有用”扩充核心。

## 4. 决策流程

```text
遇到新字段、类型或事件
|
+-- A. 它控制 HTTP、轮询、后台执行、超时或重试吗？
|   +-- 是 -> Transport
|
+-- B. 丢失后会改变理解、执行、续接、计费、安全或 round-trip 吗？
|   +-- 否 -> 请求侧 Provider extension 或响应侧 provider payload
|
+-- C. 它在对话/内容/事件序列中有独立位置和顺序吗？
|   +-- 是
|       +-- 语义稳定且 Provider 无关 -> Semantic Kernel
|       +-- 语义尚未成熟 -> Typed Incubation 或有序 Native
|
+-- D. 它是跨 Provider 同构的生成或行为控制吗？
|   +-- 是且成熟 -> Portable Controls
|   +-- 否或未成熟 -> Provider request extension
|
+-- E. 后续 fixture、映射和消费者证据充分吗？
    +-- 是 -> 提交升格提案
    +-- 否 -> 继续留在孵化区或扩展区
```

## 5. 归属定义

### 5.1 吸收进语义内核

同时满足以下条件时，优先进入核心代数类型：

- 消费者必须区分处理；
- 在序列中有身份、位置或顺序；
- 语义可独立于 Provider 定义；
- 有稳定不变量和映射；
- 证据足以承担公共 API 兼容成本。

典型示例：`Text`、`Thinking`、`ToolUse`、`ToolResult`、`Refusal`、结束原因。

### 5.2 吸收进可移植控制

适用于不会形成新内容节点，但跨 Provider 存在稳定等价语义的请求控制。例如最大输出 token、采样参数、结构化输出或已经验证同构的推理配置。

控制值不同不等于内容语义不同。尤其要区分：

- **能力声明**：模型是否支持并行工具调用；
- **请求控制**：本次请求是否允许并行工具调用；
- **响应事实**：本次响应实际产生了多少工具调用。

三者不得复用同一字段表达。

### 5.3 类型化孵化区

满足以下任一条件时先孵化，不直接扩充核心：

- 消费者确实需要它，但跨 Provider 模型尚不稳定；
- 只有一个 Provider 提供，未来形态仍可能变化；
- 需要比裸 `Json` 更强的约束，但尚未形成版本承诺；
- 工具声明侧和输出事件侧尚不能同时闭环。

孵化类型必须标明实验状态、原始 Provider 映射和升格条件。

### 5.4 三类“逃生舱”

不得把所有未知数据都塞进同一种 Map。

#### 语义逃生口：`Native`

用于未知但有位置、有顺序、有身份的语义节点。必须保留类型标签、原始 payload 和原始相对顺序。

#### 请求扩展：`LucentRequest.extra`

用于 Provider 专属请求控制参数。必须：

- 使用 Provider 命名空间，避免不同 Provider 同名冲突；
- 由目标适配器显式读取并写入 Provider 请求；
- 定义与标准字段冲突时的优先级；
- 对不支持的目标 Provider 明确报错或忽略策略；
- 通过往返测试证明不会被静默丢弃。

#### 响应附载：`LucentResponse.provider_payload`

用于只读的 Provider 原始附加信息、诊断数据或尚未标准化的响应字段。业务代码不得默认依赖其跨 Provider 可移植性。

如果某字段影响下一轮续接、工具执行、计费或安全判断，它不能仅作为无约束诊断 payload 后被遗忘；必须提供明确访问和保留契约。

### 5.5 传输层

`background`、polling、HTTP headers、timeout、retry、连接复用和 SSE 传输策略属于 Transport。只有传输产生的可观察语义事实，例如结构化错误或已完成状态，才映射回 IR。

## 6. 兼容性规则

“字段是 Optional”只证明部分 JSON 数据兼容，不等于公共 API 完全兼容。

Agent 必须分别评估：

| 兼容层 | 要求 |
|---|---|
| JSON 数据兼容 | 新字段缺失时旧数据仍能解析；未知字段策略明确 |
| 构造 API 兼容 | 优先通过稳定构造器创建公开 struct；新增字段不得迫使所有调用方修改 |
| 模式匹配兼容 | 给公开 enum 新增变体可能破坏穷尽匹配，必须按 breaking change 评估 |
| 语义兼容 | 已有字段和变体的意义不得改变 |
| 往返兼容 | 支持范围内不得因经过 IR 而丢失可观察行为 |

v1 内不得仅凭存在 `_ => ()` 的写法就认定新增核心枚举变体是非 breaking。证据不足的新语义应先进入 `Native` 或孵化区，成熟后通过明确版本决策升格。

## 7. Agent 执行清单

任何新增或修改 Lucent IR 字段、枚举变体、工具模型、流事件、`extra`、`provider_payload` 或 capability 的任务，Agent 必须：

1. 收集目标 Provider 的官方字段定义和真实 fixture，不凭字段名猜语义。
2. 查找所有现有 Provider 的同构或相近概念。
3. 写出消费者义务：谁读取它，值不同会采取什么动作。
4. 执行五道判定门，并记录每道门的结论。
5. 选择且只选择一个归属层；不得同时在核心和扩展中维护两个真相来源。
6. 定义编码、解码、流式、目标不支持和 round-trip 行为。
7. 评估公开 struct 与 enum 的源码兼容性。
8. 更新 `docs/lux-ir-design.md`，使形式规范与决策一致。
9. 更新所有受影响的 Provider 适配器和调用方；不得保留未使用的兼容别名或旧路径。
10. 添加跨协议 fixture/行为测试，至少覆盖：
   - Provider -> Lucent；
   - Lucent -> Provider；
   - 支持范围内的 round-trip；
   - 未知值或目标不支持时的显式行为。
11. 运行项目规定的 `moon info && moon fmt` 和相关测试，确认 `.mbti` 变化符合预期。

## 8. 升格标准

扩展或孵化概念只有同时满足以下条件，才可升格为标准字段或核心类型：

- 至少两个独立 Provider 存在可证明的同构语义，或它是消费者无法回避的单 Provider 新语义；
- 至少一个真实消费方需要稳定读取它；
- 名称、类型、默认值和降级行为明确；
- 双向适配及流式映射（若适用）已验证；
- 有测试保护不变量；
- 已评估兼容性和 schema 版本影响；
- 升格后能够删除对应的重复扩展路径，保持单一真相来源。

出现以下情况时不得升格：

- 仅为提高字段覆盖率；
- 只有文档猜测，没有 fixture；
- 只能用某 Provider 的字段名解释；
- 无法说明消费方如何使用；
- 尚未定义不支持时的行为；
- 需要大量 Optional 字段才能勉强统一互不相同的概念。

## 9. 快速判断句

遇到新字段时先问：

> 删除它以后，Prism 用户是否仍能正确理解、执行、续接并无损转发这次交互？

- **不能，且语义稳定、Provider 无关**：吸收进标准类型。
- **不能，但概念尚未成熟**：进入类型化孵化区或有位置的 `Native`。
- **能，只控制某个 Provider 的请求行为**：进入命名空间化请求扩展。
- **只需保留原始响应细节**：进入响应附载。
- **改变网络调用生命周期**：进入 Transport。

最终目标不是让核心字段最多，而是确保：**标准部分稳定，未知部分不静默丢失，扩展升格有证据、有不变量、有版本纪律。**
